## 1. 目的與交付範圍

總經理和主管打開 OrgMaster，就能在一張和既有 XMind 相近的心智圖上看見部門如何分工、每項工作對應哪一章管理辦法，以及回饋如何回到下一個部門。讀者應能在同一畫面回答「採購由誰承接」和「客戶現場漏水如何帶動下一次組裝改善」。

本任務在 OrgMaster 交付第一版唯讀關係圖。首批資料以六部門、33 個職掌大項、116 項細部職掌及附錄 A 的主要歸章為驗收基準，產品依所選版本的實際資料產生。

| 首版交付 | 行為 |
| --- | --- |
| 同圖閱讀 | 一張圖查閱部門、兩層職掌、四部十二章與五條具名飛輪，透過篩選及原位展開聚焦內容。 |
| 辦法對應 | 從職掌明細開啟公司閱讀版，也可從原文反查承接職掌。共通辦法依大項維護，專項辦法依細項維護。 |
| AI 盤點 | 具資格的主管手動分析一個完整組織版本，在圖上查閱當次發現，關閉後恢復原檢視。 |
| 首批建置 | 六部門與中長期能力先整批進同一份規劃草稿，以虛構委外案走讀，真實辦法先核對採購、驗收與付款。 |

首版內容到部門與職掌。職掌名稱沿用已確認版本，畫面省略職掌編號與工作量欄位。首批草稿建置是一次明確的資料建立操作，平時圖上操作維持唯讀。

後續才進入的範圍如下，保留資料相容所需的接點，不列入首版交付。

- 職位與人員分配。
- 同圖編輯歸章、交接與線形，以及供同一版本讀者共用的排版保存，依第 6.2 節延伸。
- Platform 章目直接帶入 OrgMaster 篩選，以及管理辦法正文逐條比對。

### 2.2 明細、原文與盤點

點職掌開啟同圖明細，列出內容、已確認的規劃標記與有權閱讀的明示辦法。文件入口只放明細內。共通與專項文件分組、公司閱讀版及原文反查的完整規則統一見第 4 節。

窄視窗將章節與顯示條件收在「篩選與顯示」內，展開後可用鍵盤選擇，收合後仍在同一張圖閱讀。桌面寬面板保留四部十二章同時可見。檢視頁籤可換行，畫布依工作台剩餘高度配置。

主管按需發起全公司 AI 盤點，畫面篩選只影響看圖。可用結果直接標在原圖，點標記可看涉及兩端與理由，方便自行截圖。成功時暫時顯示全圖並展開相關分支，關閉後恢復原篩選與展開狀態，等待或失敗時保留當前檢視。資格、輸入範圍、結果分類、暫存及還原契約統一見第 5 節。

### 3.1 資料模型與相容讀寫

在 `OrgDirectoryState` 增加可選的 `dutyMap` 子物件，內容隨同一份組織版本文件保存，子物件帶 `schemaVersion: 1`。細部職掌的名稱及說明沿用現有 `Duty`，其部門與大項隸屬由下表的 `memberships` 表達。主要欄位如下。

| 集合 | 欄位及用途 |
| --- | --- |
| `groups` | `id, departmentId, title, order`。保存職掌大項，部門 ID 引用該版本既有部門。 |
| `memberships` | `dutyId, groupId, order, planningStage`。每項細部職掌在圖上有一個所屬大項，`planningStage` 為 `long-term` 或 `null`，沿用人工確認資訊。 |
| `chapterLinks` | `id, target, chapterId, kind, explanation`。`target.kind` 為 `group` 或 `duty`，`target.id` 引用對應節點，連結的 `kind` 為 `primary` 或 `collaboration`。每個目標最多一筆主要歸章，跨章交接可有多筆。 |
| `methodLinks` | `id, target, methodId`。職掌大項或細項與具體辦法的明示對應，同一目標與文件只保存一筆。大項共通辦法於讀取細項時合併顯示。 |
| `flywheels` | `id, title, colorKey, presentation, departmentId, steps`。`presentation` 為 `cross-department` 或 `department-cycle`，分支內循環另帶所屬部門與步驟文字。 |
| `relationships` | `id, flywheelId, fromDepartmentId, toDepartmentId, delivery, geometry`。保存九筆有方向的交付，`geometry` 可帶起終錨點、曲線控制點與標籤位置。往返交接各有獨立 ID。 |
| `departmentLayout` | `departmentId, side, order`。作為該版本左右側與同側排序的基準。`side` 為 `left` 或 `right`。 |
| `sourceBindings` | `sourceKey, target`。首次建置時保存來源路徑與實際節點 ID 的對照，供同一批資料重試與人工核對。 |

首版沿用目前 V8 文件的可選擴充方式，缺少 `dutyMap` 的舊文件可正常讀取。關係圖顯示「此版本尚未建立部門職掌對應」並沿用既有職掌工作台入口。伺服器在保存舊畫面送來、未帶此子物件的文件時，保留同一 revision 已有的 `dutyMap`，再一起驗證及保存。明確清空須由能辨識此欄位的維護動作提出。

更新解析、正規化、複製草稿、匯出與再載入的流程，完整保留新增資料。檢查組織端參照是否存在、細項是否重複隸屬、大項是否屬於正確部門、章號是否在章目中，以及交接端點與飛輪是否有效。參照衝突時保留原文件並回報受影響節點。這些檢查驗證資料完整性，歸章是否合理仍交由主管與按需 AI 判讀。

既有維護入口刪除或移動被引用的職掌、部門時，同步處理受影響的隸屬、連結與排版，與原操作一起驗證及保存。若舊客戶端送來的修改會留下斷裂參照，回傳衝突並保留伺服器資料，讓該客戶端重新載入後處理。

保存沿用 `saveWorkspaceVersion` 的版本 revision、交易與 verified Principal writer。首次建置在指定規劃草稿中核對來源 ID，將職掌與全部對應一次保存。重試先讀回草稿並依 `sourceBindings` 辨識已完成項目。名稱相同但 ID 或部門有歧義時，列出原始路徑供核對。業務資料採用現有 persistence artifact 管道，首版資料設計可使用既有版本文件承載。[文件解析及複製](../../src/documentStorage.ts) · [組織版本保存](../../server/orgmasterWorkspaceStore.ts) · [版本 API 與寫入授權](../../server/orgmasterApi.ts)

### 3.2 首批草稿與中長期能力

**來源對應。** 首次建置以附錄逐項對照該組織版本的真實 ID。名稱可供人工核對。遇同名或歸屬衝突，標出待對應項並保留其原始路徑，確認前保留原資料。來源中尚未建立的部門與職掌可新增至規劃草稿。以穩定識別保存關聯，改名後仍能追到同一節點。首版沿用既有整份組織版本閱讀權限；有權讀取該版本者可閱覽其中各部門職掌。部門選單、展開與切換飛輪只影響畫面篩選，不形成單部門資料限閱，亦不改變管理辦法本身的閱讀權限。

**首批建置於同一份規劃草稿。** 將附錄 A 的六個部門、33 個職掌大項與 116 項細部職掌放進同一份 OrgMaster 規劃草稿，包含已確認的中長期能力。各部門主管可在這張草稿圖上核對自己的職掌，以及跨部門交付與承接的兩端。建置範圍到部門職掌為止。分工確認後，再依 OrgMaster 既有版本流程生效。

**中長期規劃標記。** 在所選版本的職掌資料中，僅對主管已確認屬於中長期規劃的細項加註「中長期規劃」。主管展開該職掌的明細時才顯示標記，全圖總覽保留原有部門與大項。標記表示公司已將該能力納入規劃；實際啟動時間另依業務事實確認。

## 4. 管理辦法雙向查閱

**具體辦法的閱讀入口。** 由 OrgMaster 在所選組織版本維護職掌大項或細項與辦法 ID（`methodId`）的明示對應。同一項職掌可對應多份辦法。用具閱讀權限的公司閱讀清單解析名稱，在明細中逐份提供入口。工作台以 `view: 'readable'` 開啟既有文件面板並保留組織版本與原圖 context；獨立文件網址沿用 `buildManagementMethodDocumentUrl(methodId, 'readable')` 的公司閱讀語意。開啟時再由文件端核對閱讀資格與目前提供公司閱讀的版本。即使職掌來自組織草稿，文件仍取公司閱讀版。辦法原文僅供讀者查閱，AI 盤點沿用第 5 節的輸入範圍。[管理辦法路由](../../src/managementMethods/route.ts) · [管理辦法閱讀介面](../../src/managementMethods/apiClient.ts)

**雙向查閱共用同一份對應。** 從心智圖進入辦法時保留所選組織版本。在「職掌對照」依版本與目前辦法 ID 反查職掌明細使用的同一組連結，套用職掌閱讀權限後按部門列出，每項職掌在所屬部門只出現一次。依組織端的職掌隸屬取得部門，因此暫無職位或人員指派的職掌也能顯示。既有面板的職掌搜尋仍可使用，搜尋命中與本辦法的明確對應須能區分。[既有職掌對照面板](../../src/components/managementMethods/ManagementMethodDutyDrawer.tsx)

**依辦法適用範圍建立對應。** 每筆連結保存目標層級（職掌大項或細部職掌）以及該節點在所選版本的穩定 ID。共通辦法涵蓋整個大項時，只在大項建立一筆連結。辦法只適用大項下的部分工作時，逐一連到受規範的細項。同一份對應供職掌查閱與辦法反查使用。

**細項明細沿用大項連結。** 開啟細項時，以所選組織版本的隸屬關係找到其上層大項，分別讀取這兩個節點明確連結且讀者可閱的辦法。共通辦法只在大項維護一次。即使六個細項的讀者都能看到同一份共通辦法，從辦法反查時仍只列原先連結的大項。

## 5. 按需 AI 盤點

### 5.1 發起資格與組織版本

**發起資格。** 總經理與各部門主管，若具所選整份組織版本閱讀權限及全域 `orgmaster.duty_map.review` 業務權限，均可自行發起全公司 AI 盤點。一般讀者同樣可查閱有權閱讀版本的各部門職掌，但閱讀資格不等於盤點資格。服務端在送出模型請求前，依 OrgMaster 的有效任用與權限核對發起資格及資料範圍。

**盤點版本。** 沿用 OrgMaster 的版本選擇器。符合第 5.1 節資格的主管可選現行版，也可在草稿生效前盤點自己有權完整讀取的草稿。每次請求綁定一個版本 ID，由該版本取得全公司的部門、職掌、歸章與交接資料。結果在圖上直接標明「現行版」或「草稿」及版本名稱，使截圖保有版本資訊。切換版本時收起前一版的結果。晚回的分析只屬於原請求的版本。[既有版本選擇器](../../src/components/VersionSwitcher.tsx)

封存草稿沿用既有工作區的可讀性。有權讀取者仍可看圖與反查；同時具盤點資格者可手動分析。這些唯讀操作不改封存狀態或文件內容，亦不給予維護權限。

一般讀圖依既有工作區閱讀資格。AI 發起能力在既有權限目錄增加 `orgmaster.duty_map.review`，透過原有任用與授權方式配置給具全公司職掌閱讀資格的總經理及部門主管。服務端沿 verified Principal 的既有有效任用與權限判定，名稱相同的職位或一般讀者也須符合這項動作權限。`canReview` 只是前端呈現依據。辦法閱讀另驗證既有 `orgmaster.management_method.read_readable`，其授權邊界沿 DEV-032。

新增動作須核對既有權限目錄同步、治理草稿發布及初始化來源契約的相容性。已套用的初始化 SQL 與封存來源保持原樣，沿既有契約處理後續目錄增量。僅將權限常數加入程式或啟用本機測試身分，不足以證明真實主管已具發起資格。

`orgmaster.duty_map.review` 屬普通業務動作，與既有十五項初始化管理能力分開。具治理權限者透過既有命令登錄來源目錄中的完整定義，授予普通業務角色、明示任用合格 Employee 並採全公司 scope，發布後才生效。這項動作不自動加入管理員能力。前端既有 `orgmaster.frontend-permission-projection.v1` 維持原集合，關係圖依自己的 `canReview` 顯示盤點入口，服務端每次仍重新核對有效權限。

### 5.2 分析範圍與圖上結果

這是低頻、由主管發起的分析。OrgMaster 依目前組織版本與讀取權限，交付所選範圍、職掌名稱與說明、部門與大項路徑、已登錄的對應，以及四部十二章的章號與章名。日常開圖、展開與篩選只呈現既有資料。首版估工排除自動盤點排程、程式歸章或缺口判定引擎，以及模型失敗時的規則替代流程。

全公司盤點以指定版本的完整部門資料為範圍，包含目前在圖上收合、隱藏或被篩掉的分支。主管只需發起一次，AI 可對照不同部門的交付與承接。部門選單不縮減本次分析範圍；只有部門 scope 的盤點任用不足以取得全公司盤點資格。若具備發起資格但資料載入不完整，提示本次全公司盤點未完成。

結果只供當次查看。使用者若想把某項發現帶到會議中，自行使用裝置的截圖功能。產品不提供專用複製或截圖按鈕，也不保存 AI 結果供下次重開或其他主管調閱。

用本次回覆所引用的職掌或章節 ID 將發現定位到圖上。標記及圖旁說明標示「AI 盤點」，與既有歸章、飛輪交接共用同一畫面。盤點結果沿用該版本的全圖排版，按需展開標記所在的分支。關閉時一起移除本次標記與說明，恢復先前的部門、章節、飛輪篩選與分支展開狀態。這次切換只影響當次畫面。

AI 依工作內容判讀主要歸章、跨章協作與可能的缺口。每筆意見應列出職掌或章節、已登錄的事實、建議及理由。現有對應合理時可建議維持，資訊不足時回覆「待確認」並說明缺少什麼。分析以提供的章目和職掌為限，逐條比對辦法正文屬另一項用途。OrgMaster 核對模型引用的職掌與章號是否在允許範圍，將有效回覆標為「AI 分析」供主管判讀。只有主管透過既有維護流程修正的資料，才會成為正式關係。

模型未設定、逾時或回覆無法驗證時，顯示「本次 AI 盤點未完成」，保留原圖及已登錄的關係，主管可稍後再發起分析。工程上可參考既有推薦服務的模型呼叫方式。既有管理辦法草稿產生器仍依 DEV-032 的文件建立契約運作。[既有推薦服務](../../server/employeeRecommendationService.ts) · [管理辦法文件契約](DEV-032-management-method-system.md)

手動盤點時，一併送出所選版本各職掌已確認的規劃標記。若某章只有標為「中長期規劃」的職掌承接，AI 可指出已有規劃，並說明現行承接是否有資料佐證。未標記只表示沒有這項註記，不能據以推定已在執行。

### 5.3 模型回覆與請求生命週期

模型設定沿用既有服務端供應商設定方式，為本功能選定可容納全公司資料的模型及上下文上限。服務端只送職掌與交接分析所需的資料。組織版本、規劃標記及章目全部綁定至本次請求，輸入的名稱與說明視為待分析資料。超出模型容量時回報本次未完成，保留完整分析範圍。

模型回覆採嚴格 JSON，主體為 `{ findings: [...] }`。每筆 finding 包含以下欄位，結構驗證可沿用既有 Zod 與 JSON Schema 工具。

| 欄位 | 格式與意義 |
| --- | --- |
| `kind` | `duty-unmapped`、`chapter-collaboration-only`、`chapter-no-duty`、`handoff-gap`、`mapping-suggestion` 或 `needs-confirmation`。用於既有決策所需的呈現。 |
| `nodeRefs` | 節點的 `kind, id` 參照陣列，`kind` 為 `department`、`group` 或 `duty`。 |
| `chapterIds`、`relationshipIds` | 本次章目與交接中的有效識別陣列，可為空。每筆至少有一個節點、章節或交接參照可定位。 |
| `summary`、`observed`、`suggestion`、`reason` | 純文字，分別顯示發現、提供資料中的事實、建議與理由。資訊不足時用 `needs-confirmation` 並說明缺少的依據。 |

OrgMaster 為各筆有效 finding 產生當次 ID，回應外層帶 `requestId, versionId, versionName, versionKind, revision, chapterCatalogVersion, generatedAt, findings`。外層版本資訊由服務端填入。引用超出本次範圍、JSON 結構錯誤或內容無法定位時，整次顯示未完成。空 `findings` 顯示「本次 AI 未提出發現」。

同一讀者在一次盤點完成前沿用進行中狀態，前端連點共用同一請求。服務端限制同一 Principal 的重複進行中請求並回報忙碌狀態，模型 SDK 關閉自動重試。採既有可中止的模型呼叫方式，單次等待上限為 60 秒。供應商支援時使用既有 `store: false` 選項。應用程式將回覆留在當次畫面記憶體中。

送模型前及結果回來時，服務端重新核對原組織 revision、完整閱讀權與盤點資格，並由認證層綁定的 request 專屬可信函式重驗原 Principal、Employee、session 與 epoch。等待期間登出、撤銷、停用、逾期或換成其他 session 時不交付結果；身分權威不可用或缺少可信重驗函式時回報未完成。沿用既有正式、本機 sandbox 與明示開啟的測試認證介面，不接受前端宣告已重驗。

前端同時比對 `requestId`、`versionId` 與 `revision`，切換版本、關閉結果或離開畫面時取消請求並清除當次結果。晚回結果保留其原請求歸屬。主管重新開啟時可自行發起新分析。這份服務沿用推薦服務的呼叫技術，分析流程依本節的按需 AI 契約處理。[既有模型呼叫與引用驗證](../../server/employeeRecommendationService.ts)

模型供應商及模型名稱沿用部署環境設定。實際主管的任用與權限沿既有管理流程維護，實際辦法依第 7.1 節在首輪試用核對。

服務端使用既有 `OPENAI_API_KEY`，模型由 `ORGMASTER_DUTY_MAP_MODEL` 指定；留白時可沿用 `ORGMASTER_MANAGEMENT_METHOD_MODEL` 的模型名稱。兩者都未指定模型，或未配置供應商時，回報未設定，不產生規則替代結果。範例設定見 `.env.example`，不把金鑰放入前端或證據。完整版本的 JSON 以 UTF-8 計算，首版單次輸入上限為 256,000 bytes，超過上限整次回報未完成。職掌缺少可定位的部門大項隸屬時，也回報來源不完整，不能默默略過這些職掌。

## 6. API 與實作接點

### 6.1 閱讀介面及工作台路由

規劃三個介面，由 OrgMaster 服務端取得資料與權限後回傳。所有回應均帶組織版本 ID 與 revision，敏感回應使用 `Cache-Control: no-store`。

| 介面 | 請求與結果 |
| --- | --- |
| `GET /api/orgmaster/duty-map?versionId=...` | 讀取選定版本的部門、大項、細項、歸章、飛輪、排版及章目來源版本，回傳讀者可見的圖形投影與 `canReview`。人員名冊與職位指派不加入這份投影。 |
| `GET /api/orgmaster/duty-map/method-links?versionId=...&methodId=...` | 核對該辦法的公司閱讀權限，反查同一版本的 `methodLinks`，回傳可見的部門路徑、目標 ID 與層級。辦法停止提供閱讀時沿既有文件讀取規則處理。 |
| `POST /api/orgmaster/duty-map/reviews` | 請求為 `{ versionId, expectedVersionRevision, chapterCatalogVersion, requestId }`。服務端重取該版本的完整資料，核對第 5.1 節資格與 revision，再分析全公司。回傳格式見第 5.3 節。 |

新增 `dutyView=map`，沿用工作台 context 保存部門、章節、飛輪、選中節點與展開狀態。由 `moduleRegistry` 解析、寫出及驗證參照，無效篩選回到可閱讀的預設值。圖上開啟辦法時攜帶所選組織版本及返回檢視，閱讀頁返回後恢復同一位置。畫布資料取得失敗時保留可重試入口，資料尚未建置與讀取失敗各有清楚訊息。

API 的輸入錯誤回 400、缺少有效登入回 401、資格不足回 403。版本不存在或文件已停止提供閱讀時，沿既有不可讀取處理並保護文件資訊。資料 revision 已改變回 409，重複進行中的盤點回 429，模型回應無效回 502，模型未設定或服務暫時不可用回 503，模型逾時回 504。前端將 AI 失敗對應至「本次 AI 盤點未完成」，保留原檢視與已登錄關係。[工作台路由](../../src/workspace/moduleRegistry.ts) · [既有權限目錄](../../src/governance/aiPdmCatalog.ts) · [管理辦法授權](../../server/managementMethodAuthorization.ts)

### 6.2 ProJED 幾何重用與後續編輯

首版由 OrgMaster 讀取指定版本的組織資料，將可見節點、交接與線形交給畫布繪製。優先抽用 ProJED 已有的座標換算與曲線計算。未來開放編輯時，沿用同一張圖與同一組關係 ID，由 OrgMaster 處理寫入。

| 責任 | 開發方式 |
| --- | --- |
| 畫布與線形 | 共用程式接受節點位置、起終點、錨點、曲線控制點及樣式，產生曲線、箭頭與標籤位置。ProJED 的控制點拖曳可供後續編輯介面沿用。首版只讀取線形並繪製，接入時優先抽取能獨立運作的函式，避免帶入看板與任務狀態。 |
| 業務資料 | OrgMaster 持有部門、職掌、歸章與飛輪交接。每筆交接在組織版本內有獨立 ID，記錄所屬飛輪、來源、去向與交付內容。同一對部門可以在同一飛輪往返，也可以在不同飛輪各有交付。篩選只決定哪些 ID 可見。 |
| 後續編輯與保存 | 拖曳控制點調整該交接的線形，保留其 ID、端點、方向及交付內容。改歸章、交接對象或交付文字屬業務變更，由 OrgMaster 依可編輯版本、權限與版本衝突檢查儲存。ProJED 的圖上註記依看板存於瀏覽器 `localStorage`，公司共用關係則由 OrgMaster 隨組織版本提供給讀者。 |
| 後續共用排版 | 每個組織版本共用一份排版。有權限的人儲存交接線形與標籤位置後，每位可讀取該版本的使用者重開都會看到調整結果。篩選產生的暫時位置只用於當次顯示。 |

**重用判斷的依據。** ProJED 新增註記線時，以兩端節點查找既有連線，交換方向仍會命中同一筆。將第 7 節的九條有向交接放在同一看板，代入該判斷後只能建立四條。另以橘色飛輪的往返線測試曲線函式，兩線使用預設控制點時標籤位置重合，分別指定控制點後可以分開。以上為函式層驗證；完整畫布在 OrgMaster 的呈現列入第 8 節驗收。

程式定位以 ProJED `0a51222` 的 `src/components/MindMap/` 為準。座標與曲線見 `mindMapCoordinateSystem.ts`、`mindMapGeometry.ts` 的 `makeRelationshipPath`。新增時的重複判斷見 `mindMapRelationshipCommands.ts` 的 `findExistingNoteRelationship` 及 `MindMapView.tsx` 的呼叫處。瀏覽器儲存見 `mindMapRelationshipStorage.ts`。

後續編輯版的共用排版驗收採同一個可編輯組織版本。編輯者把橘色往返線與標籤拉開並保存，另一位有閱讀權限的主管重開、套用相同篩選，也能看到分開的線與標籤。切到其他版本時呈現該版本自己的排版。

正常入口走讀使用第 7.1 節的四份虛構辦法及五筆明示連結。應能核對部門數、大項數、細項數、交接方向、請求所屬版本及是否發生業務寫入，並留下可定位的測試或畫面證據。A08 的真實公司辦法核對與模型分析品質各自如實標示，不將示例或測試回覆計為真實業務確認。

資料保存衝突、引用無效或權限不足時，停止受影響的寫入或分析，保留原版本並顯示原因。未知寫入結果先讀回，按已保存的來源對應判斷是否完成。其餘安全且獨立的閱讀驗證可繼續。本任務不包含正式發布、正式資料匯入或正式環境模型設定，這些動作沿專案既有授權及發布契約。

## 8. 驗收條件

驗收在隔離資料與實際工作台入口執行。下表保留原有 26 項情境；A05、A14 依 2026-11-26 使用者選擇 A，定案為整份版本閱讀、部門選單只作篩選，原限閱提案可由 Git 歷史追溯。模型測試回覆用於驗證引用、呈現與失敗行為，真實模型的分析品質另以供應商實際回覆核對。

| 案例 | 情境 | 可觀察的結果 |
| --- | --- | --- |
| A01 | 從 OrgMaster 職掌工作台直接進入 | 同一畫面有公司、六個部門、33 個大項及四部十二章篩選。以本次資料全部展開時有 116 個不重複細項。這些數量是此版本的測試基準，程式應依資料產生。 |
| A02 | 首批職掌整批進入草稿 | 在隔離資料中建置後，重開同一份草稿，依附錄 A 核對六個部門、33 個大項及 116 個細項，包含中長期能力。選橘色飛輪可讀到生產與研發的雙向交接。比對建置前後，現行版的職掌相同，新增職位與人員指派均為零。 |
| A03 | 明細與 AI 使用同一份規劃標記 | 在測試草稿為一項職掌加註「中長期規劃」，同部門另一項留白。開啟總覽時兩項均無標記，展開明細時只有前者顯示標記。手動盤點後，核對模型輸入與該版本兩筆資料一致，回覆能區分已規劃的能力與有執行證據的工作，並將缺乏依據的執行情形列為待確認。 |
| A04 | 查閱驗收依據 | 在測試草稿中將「進料與委外品質驗收」明確連到一份已有公司閱讀版的辦法，另放一份同章但未連結的辦法。明細應只列出前者。即使文件另有未提供的修訂，點入仍讀到公司閱讀版。以無文件閱讀權的身分查看時，明細不透露文件名稱或連結。若開啟前已停止提供閱讀，舊連結也無法讀取原文。 |
| A05 | 從同一份辦法查兩個部門 | 在隔離草稿將生產部「委外加工與外部服務交付管理」及研發部「進料與委外品質驗收」連到同一份測試辦法，兩項皆無職位指派。由任一職掌開啟原文，「職掌對照」應列出兩個部門及各自的職掌。具該整份版本及辦法閱讀權的一般讀者也能反查兩個部門；部門畫面篩選不改變此閱讀範圍。移除草稿中的生產部連結並重開，兩端同時反映移除，研發部對應仍可雙向查閱。 |
| A06 | 共通辦法與專項辦法 | 在測試草稿把一份共通辦法連到研發部「品質策劃、檢驗與放行」，另一份專項辦法只連到其下的「進料與委外品質驗收」。從大項與該細項明細分別開啟對應原文。反查共通辦法只列一筆「職掌大項」，即使其下有六個細項。反查專項辦法只列一筆「細部職掌」，路徑可辨認其部門與上層大項。 |
| A07 | 細項明細可辨認兩種依據 | 沿用共通辦法與專項辦法案例的兩份測試文件。開啟「進料與委外品質驗收」，專項文件出現在「本細項辦法」，上層文件出現在「所屬大項共通辦法」，兩者皆可點閱。改開同一大項的「量測設備適用性與失準影響管理」，兩份測試文件中只看得到共通辦法。重新讀取對應資料仍只有原來兩筆。 |
| A08 | 首輪辦法核對 | 依第 7 節沿同一件委外案查閱發包、驗收、對帳與付款。三個部門各段均能指出已核對的辦法原文，或具體說明仍缺的依據。對已有明示連結的文件，從職掌開啟原文、從辦法反查適用職掌，兩端對應一致。 |
| A09 | 先用虛構委外案走讀 | 在隔離測試資料內使用第 7 節四份示例辦法與五筆連結，各職掌均維持零職位及人員指派。驗收明細可分別開啟專項說明與共通辦法，對帳付款辦法可反查生產與財務兩端。重開同一草稿後，仍是原五筆連結。這項案例供實作後驗證使用。 |
| A10 | 零職位指派、部門篩選與局部展開 | 有部門歸屬且無職位指派的職掌照常可見。展開兩個大項後可同時閱讀，關閉章節標記後兩者仍展開。 |
| A11 | 選章、反查與無結果 | 選第 04 章能看到上述四個部門及各自範圍。點職掌旁的同章標記可聚焦同一集合。選無對應的部門與章節會顯示空結果，清除後恢復全圖。 |
| A12 | 日常閱讀與手動啟動 | 開圖、收合分支、切換部門與章節時，核對模型呼叫為零，畫面只顯示已登錄的關係。主管按「請 AI 盤點」後，才送出所選範圍的資料。 |
| A13 | 一次盤點全公司 | 用具全公司職掌閱讀權限的部門主管帳號，先篩到只看生產部，再發起一次全公司盤點。核對分析輸入涵蓋附錄的六部門、33 個大項、116 項細部職掌與十二章，能同時引用生產部與研發部的交接。 |
| A14 | 發起資格與閱讀範圍 | 具整份版本閱讀權及全域盤點權的總經理與部門主管皆能自行發起。具版本閱讀權但沒有盤點權的一般讀者，以及只有部門 scope 盤點任用的主管，仍可查閱該版本全部部門、選部門篩選並清除還原。分別以這兩種身分直接請求盤點，服務端應拒絕，模型呼叫數均為零。無版本閱讀資格者不能取得圖形或盤點資料。 |
| A15 | 草稿生效前盤點 | 在隔離測試資料中，讓同一筆零件採購職掌在現行版與草稿分屬不同部門。以符合第 5.1 節資格的主管分別發起盤點，確認兩次模型輸入各自只含所選版本的歸屬。草稿結果在對應部門標記，圖上可同時讀到「草稿」與版本名稱。若在等待時切回現行版，晚回的草稿標記不出現在現行圖上。以無權讀取該草稿的主管請求時，模型呼叫數為零。 |

| A17 | 跨部門發現直接定位 | 在未套用篩選的全圖，令模型測試回覆引用生產部的「現場維修、保養與改造執行」及研發部的「產品操作、安裝與維護技術文件」，說明需要核對誰把修復經驗轉成組裝指引。盤點完成即在相關分支看到本次標記。點選任一端，可同時辨認兩項職掌並讀到同一則理由。關閉結果後，原有的交接線與職掌仍在。 |
| A18 | 從篩選檢視進出盤點結果 | 先選財務部、展開一個職掌大項，再發起全公司盤點。等待時仍看財務部。沿用跨部門發現案例的生產與研發測試回覆，成功後確認六個部門皆可見，並可從圖上讀取該則跨部門發現。關閉後回到財務部，原大項仍展開，本次標記已移除。以逾時回覆重試此案例時，原檢視應一直保留。 |
